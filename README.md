# Data Hydration Gap Model

[![Live app](https://img.shields.io/badge/Live%20app-datafoundation.streamlit.app-blue?logo=streamlit)](https://datafoundation.streamlit.app/)

Interactive decision-support tool for the game-theoretic model introduced in:

> **Besanson (2026) — The Data Hydration Gap: A Formal Model of Underinvestment in General-Purpose Data Products Under Decentralized Governance**
> [arXiv:2604.00218](https://arxiv.org/abs/2604.00218)

---

## What problem does this solve?

Data mesh architectures delegate data product ownership to business domains. The paper proves formally that rational domain teams will systematically *underinvest* in making their data products reusable — even when doing so would benefit the organization as a whole. This is a **public-goods externality problem**: each domain captures only its own benefit from standardization, but ignores the value that generality creates for every other domain and consumer.

The result is a "data mesh trap": decentralized governance produces a siloed bronze layer instead of a reusable silver layer.

**This tool lets CDOs and data leaders:**
- Diagnose whether their organization is in the trap, or close to it
- Quantify the annual welfare loss and accumulated technical debt in dollar terms
- Identify the cheapest governance intervention to close the gap
- Compare four governance regimes (Pure Mesh, Centralized, Federated Incentives, Hybrid)
- Project how costs compound as the organization adds more domains

## How to use the app

### Simple mode (CDOs and business leaders)

Answer five plain-language questions about your organization:

| Question | What it captures |
|----------|-----------------|
| How many business units own data? | Scale (N, M) |
| How often do projects need cross-department data? | Spillover intensity (λ, ω̄) |
| How mature is your data governance? | Cost structure (κ, γ_g, β) |
| How good is your raw source data quality? | Baseline quality (q*, α) |
| How expensive is one custom integration pipeline? | Technical debt rate (τ, P̄) |

Industry presets (Retail, FinServ, Healthcare, SaaS/Tech) let you start from a calibrated baseline.

The app returns a **color-coded diagnosis** (trap / severe / moderate / near-optimal), an estimated annual dollar loss, a recommended governance action, and the top 1–3 concrete steps to improve your score — sorted by effort.

### Expert mode (researchers and data architects)

Full control over all 11 model parameters via sliders, organized into four groups: organization structure, incentives & value, cost structure, and technical debt. Expert mode adds:

- Six KPI cards showing every model output with equation references
- Inverse solver: exact parameter changes needed to escape the trap or close the gap to 75% of optimal
- Charts of gⁿᵉ, gˢᵒ, TD, and ΔW as functions of N
- 5-year growth trajectory projecting how costs compound
- Sensitivity tornado showing which parameter drives welfare loss most
- Scenario manager: save, compare, and download multiple configurations as CSV
- AI executive summary (requires Anthropic API key) — 3-paragraph C-suite brief generated by Claude
- Shareable URL: encode the current parameter set into query parameters

## The model

All five equations are implemented verbatim in `model.py`.

### Eq. (7) — Nash equilibrium generality

```
gⁿᵉ = max{ 0,  (αβ − κ/q*) / γ_g }
```

Each domain chooses generality to maximize its *private* benefit. The numerator is the net marginal benefit from standardization after paying the fixed overhead; the denominator is the marginal cost of adding generality. The `max{0, …}` captures the trap: if fixed costs dominate, no domain invests at all.

### Proposition 1 / Eq. (8) — Social optimum

```
gˢᵒ = clip[ (αβ + (N−1)λ + Mω̄ − κ/q*) / γ_g ,  0, 1 ]
```

A central planner also internalizes the cross-domain spillover `(N−1)λ` (value created for every other domain) and the consumer term `Mω̄` (value created for cross-domain analytics teams). The gap `gˢᵒ − gⁿᵉ` is always non-negative and grows with N, λ, M, and ω̄.

### Eq. (10) — Annual welfare loss

```
ΔW = N · [ ((N−1)λ + Mω̄) · q* · Δg  −  (γ_g / 2) · q* · (gˢᵒ² − gⁿᵉ²) ]
```

where `Δg = gˢᵒ − gⁿᵉ`. The first term is the value destroyed by underinvestment; the second subtracts the cost saving from not over-standardizing. ΔW scales roughly as N², meaning every new domain added to a decentralized org compounds the loss.

### Eq. (13) — Technical debt

```
TD_total = τ · q* · N(N−1) · P̄
```

The cost of building all the custom point-to-point integrations that a general silver layer would have made unnecessary. Grows quadratically with N. Calibrated in $M using `τ` in $M per pipeline.

### Eq. (19) — Pigouvian subsidy

```
sᵢ = (N−1) · λ · q*
```

The per-domain reusability bonus that exactly corrects the externality, aligning private incentives with the social optimum. Total annual investment needed: `N · sᵢ`. The paper shows this is the minimum-cost decentralized mechanism to achieve gˢᵒ.

## Parameters

| Symbol | Name | Range | Description |
|--------|------|-------|-------------|
| N | Domains | 2–40 | Distinct business units that own data products |
| M | Cross-domain consumers | 0–50 | Analytics teams or ML projects consuming data from more than one domain |
| α | Domain analytics value | 0.1–1.0 | How heavily a domain relies on its own data products |
| β | Generality–quality synergy | 0.0–0.5 | Internal quality gain per unit of standardization (platform tooling effect) |
| λ | Cross-domain data value | 0.0–1.0 | Share of analytical value that requires cross-domain joins |
| ω̄ | Avg. consumer weight | 0.0–1.0 | Importance of each domain to cross-domain consumers |
| γ_g | Generality cost | 0.1–1.0 | Marginal cost of adding one unit of generality |
| κ | Fixed standardization cost | 0.0–0.6 | One-time overhead to begin any standardization effort |
| q* | Baseline quality | 0.1–1.0 | Quality of raw/bronze data before generalization |
| τ | Integration cost per pair | 0.0–0.2 | Cost ($M) to build one custom pipeline between two domains |
| P̄ | Avg. prob. needing another domain | 0.0–1.0 | Probability any given domain needs data from another |

Paper baseline: N=12, M=10, α=0.5, β=0.15, λ=0.4, ω̄=0.3, γ_g=0.4, κ=0.25, q*=0.6, τ=0.05, P̄=0.5. At these values the paper proves the trap condition holds (gⁿᵉ = 0).

## Governance regime comparison

The app computes net savings for four regimes, as in Table 2 of the paper:

| Regime | Achieves gˢᵒ? | Mechanism | Tradeoffs |
|--------|--------------|-----------|-----------|
| Pure Data Mesh | No | None | Zero cost; full welfare loss; TD accumulates |
| Centralized Hydration | Yes | Central team builds and owns shared products | Higher fixed cost; removes domain ownership |
| Federated + Incentives | Yes | Per-domain Pigouvian subsidy sᵢ | Lowest cost when domains have capacity; preserves autonomy |
| Hybrid | ~70% of gˢᵒ | Central standards + domain execution | Best balance for most organizations |
